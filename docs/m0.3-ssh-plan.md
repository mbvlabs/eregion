# M0.3 remote half plan: pinned SSH transport (Increment A)

**Status:** Decided for SSH · 2026-10-20
**Scope:** Increment A of [the SSH/WireGuard increments](ssh-wireguard-next.md) only.
Userspace WireGuard stays out of scope; the only WireGuard-related work here is
the dialer seam that the next increment plugs into.

This document resolves the "Remote supervision and reattachment still to decide"
list in `docs/ssh-wireguard-next.md` for SSH, and records the deferred review
findings that the local increment left open. It does not claim remote
exactly-once behaviour for WireGuard, node enrollment, or multi-node placement.

## Decision summary

| # | Question | Decision |
| --- | --- | --- |
| 1 | Node execution lifetime | Detached task plus durable journal, queried by `status`. The SSH session never owns execution lifetime. |
| 2 | Ownership fencing | The node-local effect lock and the durable effect record remain the effect fence. The transport adds a request fence (execution identity), not a distributed lease. Control-plane writes stay attempt-fenced in PostgreSQL. |
| 3 | Cancellation | No remote kill. A cancellation request is honoured at the step boundary; a detached task is left to finish and reconciled through `status`. |
| 4 | Remote state directory | `/var/lib/eregion/node`, owned by a dedicated unprivileged node account, mode 0700, files 0600. The journal is compacted; effect records are the exactly-once evidence. |
| 5 | Handshake/version | A protocol-version frame is exchanged before any request is accepted. Any mismatch fails closed. |
| 6 | Auth/privilege | Key-only authentication to a dedicated unprivileged account. No root, no sudo, no password, no agent forwarding, no PTY, no forwarding. The control plane pins the node host key. |
| 7 | Stderr tail | Bounded to 8 KiB, redacted, and only ever attached to an error detail. |
| 8 | Test fixture | A throwaway `sshd` container with a generated host key, built by a `just` recipe; tests skip cleanly without Docker. |

## 1. Node execution lifetime

**Decision: the node runs a detached task and answers `status` from a durable
journal. The SSH session is a transport, not an owner.**

The SSH transport sends one `run` request. The node:

1. checks the durable effect record and the journal for the effect key,
2. refuses to start a second live effect (the effect `flock` is the liveness
   test),
3. otherwise starts the step in a **detached child process** and answers
   `running`,
4. records the outcome in the node journal and the effect record.

The control plane then polls `status` over the same transport until the effect
reaches a terminal state. A lost stream is an explicit outcome
(`node.ErrStreamLost`): the control plane does **not** conclude that the node
stopped. The retry path always calls `status` before `run`, which is the
existing worker decision procedure and is not changed by the transport.

Why detached:

- The SSH channel, the node's `serve` process, and the control-plane worker are
  all transient. If any of them dies, the effect must still converge exactly
  once. A session-owned task would be killed by the channel closing, which
  makes "the node task outlives its caller" untestable and turns every
  disconnect into a half-applied effect.
- The detached child is started with `setsid`, its own session, and no
  inherited standard streams, so closing the SSH channel neither signals it
  nor lets it write into the channel. The request (including any transient
  secret) reaches the child through an inherited pipe, never through a file,
  an argument, or an environment variable.
- The child holds the effect `flock` while it works. A second `run` for the
  same effect key blocks on that lock and then observes the completed effect
  instead of applying it again. That is the same attach semantics the local
  transport already relies on.

Rejected alternative: *session-owned execution*. It is simpler, but it makes
the stream the source of truth, which the increment forbids, and it cannot
satisfy the "node task outliving its caller" gate.

The node task is still bounded by the host: a reboot kills it. Recovery is the
journal plus the effect record, exactly as in the local model.

## 2. Ownership fencing across control-plane instances

Three independent fences, none of which is a distributed lock:

| Scope | Mechanism | Protects |
| --- | --- | --- |
| Control plane | `SELECT ... FOR UPDATE` plus attempt equality (`mutateOwned`) | state, event, and step ordering between workers |
| Control plane | primary key `(operation_id, step)` plus a conditional update | duplicate acknowledgements and duplicate progress events |
| Node | effect `flock` plus the journal and the effect record | duplicate side effects on one host |

The SSH transport adds a **request fence**, not a lease: every request carries
the execution identity `op_<id>:<attempt>:<step>`, and the node records it in
the journal and the effect record. A controller that retries the same operation
reuses the same effect key, so it attaches to the same node-side effect instead
of creating a second one. A controller that arrives with a different execution
identity still cannot apply the effect twice, because the effect key and the
node lock decide that, not the attempt number.

What stays open: conflict scopes between *different* nodes and a lease that
coordinates several control-plane instances across hosts. River concurrency is
not a distributed environment lock. Those belong to node enrollment and
placement (M2), not to this increment. The SSH increment must not be described
as a distributed lock.

## 3. Cancellation reaching a detached node task

**Decision: there is no remote kill in Increment A.**

- A cancellation request sets `cancelling` in PostgreSQL. It is a request, not
  an acknowledgement.
- The worker checks the boundary before each step and after each
  acknowledgement. The diagnostic step declares `after_apply`, so an in-flight
  step finishes and is acknowledged, and no new step starts.
- A detached node task is never signalled. The control plane observes
  `cancelling`, waits for the effect's terminal state, and reconciles the
  completed effect.
- Cancelling the SSH call (client disconnect, worker shutdown, River job
  deadline) closes the transport session only. Because the node task is
  detached, this cannot interrupt an Apply. The transport returns an
  "outcome unknown" error, never a claim that the step stopped.
- A future step may declare `before_apply` and opt into a cooperative cancel
  RPC. Until such a step exists, the RPC does not exist: an unused remote kill
  is an outage waiting to happen, because it can land between Check and Apply.

## 4. Remote state directory and permissions

The node's state directory is node-local, shared by every node process on that
host, and never reachable from the control plane except through the transport.

```text
/var/lib/eregion/node                 0700, owned by the node service account
  journal.json                        0600  engine view of the latest attempt
  journal.json.lock                   0600
  host.lock                           0600  serialises host mutations
  locks/<sha256(effect_key)>.lock     0600  one flock per effect
  effects/<operation_id>/<step>.json  0600  durable effect record
  logs/<execution_id>.log             0600  bounded node-side task log
```

- The directory is owned by a dedicated unprivileged account (for example
  `eregion-node`). The node process never runs as root and never uses sudo.
- Every file is 0600 and every directory is 0700, so a second account on the
  host cannot read another operation's inputs hash, result, or error text.
- The control plane never reads the node's filesystem. It learns about effects
  only through `status` and `run` responses.
- **Retention.** The journal is an index and grows with every step, so it is
  compacted: terminal tasks older than the retention window are dropped unless
  they are among the most recent entries. The effect records are the durable
  exactly-once evidence and are *not* compacted automatically; pruning them is
  an explicit operator action, because dropping one would let a stale retry
  re-apply an effect. This bound is documented rather than hidden.

## 5. Handshake and version negotiation

The node protocol is a line-delimited JSON frame stream over the SSH channel's
standard input and output. The first exchange is always a handshake:

```text
client -> node  {"type":"hello","version":1}
node   -> client {"type":"hello","version":1,"node":"app-1"}
```

- The client sends `hello` and waits for the node's `hello` **before** it sends
  any request. A node that answers with a different protocol version, or that
  answers with a node name the caller did not expect, is refused: the request
  is never sent.
- The node refuses a client whose version it does not implement, and exits
  without reading a request.
- The version is a single integer. A change to the request, event, or response
  shape is a new version; the node binary and the control plane must be
  upgraded together. There is no negotiation and no downgrade.
- The host key is verified during the SSH handshake, which happens before the
  protocol handshake. A mismatch aborts the connection before any request.

## 6. Authentication and privilege policy

- **Control plane to node:** public-key authentication with a dedicated
  identity file (mode 0600) whose public half is the only entry in the node
  account's `authorized_keys` (mode 0600, owned by the node account). The
  control plane never uses an operator's personal key, an agent, or a
  password.
- **Node to control plane:** none. The node has no credentials, no database
  access, and no API token.
- **Privilege:** the node account is unprivileged. No root login, no sudo, no
  setuid helpers, no `authorized_keys` options, no `command=` restrictions
  that would be needed only because the control plane is trusted. The node
  account may write exactly one directory: its state directory.
- **Host key pinning:** the control plane pins the node's host key
  (`known_hosts` format, one entry per address). A missing pin, a changed key,
  or a host that presents a different key type than the pinned one aborts the
  connection. There is no TOFU and no "accept on first use" in this path.
- **SSH server posture** for the node: `PasswordAuthentication no`,
  `PermitRootLogin no`, `AllowTcpForwarding no`, `AllowAgentForwarding no`,
  `PermitTTY no`, `X11Forwarding no`, `MaxSessions 4`, `MaxStartups 4`.
- The remote command is fixed: the node binary is started as
  `/usr/local/bin/eregion-node serve`. The request travels over the channel's
  standard input, never in the command line, so no request value is ever
  interpolated into a shell. The command may be overridden per deployment, but
  the override is validated against a strict character set before it is used.

## 7. Stderr tail bounds

The remote command's standard error is captured into a bounded ring buffer of
8 KiB. Only the last 8 KiB is kept, so a chatty node cannot exhaust the
control plane's memory.

- The tail is redacted through the request-scoped secret registry before it
  becomes an error detail.
- Control characters are made visible; the tail is never interpreted as a
  terminal sequence.
- The tail is attached only to an error detail. A successful call does not
  carry it, and a lost stream reports the tail it had, if any, next to the
  explicit "stream lost" outcome.
- The control plane truncates node event messages to 4 KiB before they become
  operation events.

## 8. SSH test fixture

The fixture is a throwaway `sshd` container:

- base image `debian:bookworm-slim` with `openssh-server`,
- a generated ed25519 host key (the test pins exactly that key),
- a generated client key, whose public half is the only `authorized_keys`
  entry,
- the `eregion-node` binary copied in, and `/etc/eregion/node.json` written
  with the node name and the state directory.

`just ssh-fixture` builds the image. The Go test helper builds the image on
demand, starts a container with a published loopback port, and removes the
container afterwards. Every SSH test skips cleanly when Docker is missing or
the image cannot be built, so the unit suite stays runnable everywhere.

The fixture is used for the end-to-end scenarios. Deterministic protocol
failures (a host-key mismatch, a version mismatch, a stream that dies after
the request was accepted) use a small in-process SSH server in the test
package, so those cases are fast and do not depend on Docker. A TCP proxy in
front of the container injects a lost response at the transport boundary for
the recovery scenario.

## 9. WireGuard seam

The SSH transport never dials a socket itself. It asks a `Dialer` for a
`net.Conn`:

```go
type Dialer interface {
    DialContext(ctx context.Context, network, address string) (net.Conn, error)
}
```

The default dialer is `net.Dialer`. A userspace WireGuard dialer implements
the same interface and becomes the only thing Increment B has to add. The SSH
transport, the host-key pinning, the protocol, and the node binary are
unchanged by it. WireGuard remains unticked in the roadmap until it passes the
same exactly-once scenarios over its own endpoint.

## 10. Deferred review findings folded into this increment

These were found in review of the local increment and matter more once the
node is remote:

1. **Unbounded node journal.** The journal is compacted with a retention
   policy; the compaction has a test. Effect records are retained on purpose
   (section 4).
2. **`Reconcile` stopped at the first error and wrote unfenced state.**
   Reconciliation now continues past a per-operation error, collects the
   errors, and reports them together. The writes that reconciliation performs
   are attempt-fenced like every other worker write.
3. **A recovered effect recorded `applied_attempt=0`.** The step reports the
   attempt that applied the effect through `CheckResult.AppliedAttempt`; the
   engine records that attempt. `0` is documented as "the applying attempt is
   not known" for steps that cannot report it, and both cases are tested.
4. **The dispatcher hardcoded the diagnostic step.** A small step registry
   maps a versioned step ID to a step constructor. The node binary dispatches
   by step name, and the control plane builds the same step through the same
   registry, so both sides agree on the canonical inputs.
5. **Operations had no structured error code.** A failed operation now carries
   a machine-readable `error_code` in the `eregion/v1` contract, in the
   PostgreSQL operation row, and in the step rows. The code is the same
   taxonomy the CLI already uses, so `precondition_failed` is distinguishable
   from `unavailable` without parsing message text.

## 11. Non-goals for Increment A

Node enrollment, an SSH certificate authority, public-IP hardening, mesh
reconciliation, multi-node placement, distributed leases, a node-level cancel
RPC, and userspace WireGuard. The increment does not advertise a remote
exactly-once guarantee until its endpoint passes the same scenarios as the
local suite: a lost response, a killed worker, a duplicate submission, a
cancellation at a step boundary, and a node task that outlives its caller.
