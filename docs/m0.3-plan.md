# M0.3 implementation plan: node execution and recovery boundary

**Status:** Implemented for the local transport · 2026-10-20  
**Scope:** local node dispatch only; pinned SSH and userspace WireGuard remain separate
increments. This plan resolves the roadmap's "Before M0.3" decisions without claiming
remote execution or HA.

## Goal and non-goals

Run `diagnostic.test` through the same node-dispatch boundary that remote transports
will use. For one operation (one idempotency key), duplicate submissions, River
retries, and lost database acknowledgements must not duplicate its side effect. A
different idempotency key is a deliberately separate operation with a separate effect
key; cross-key duplicates remain distinct operations, as the submission contract says.

Not in this increment: SSH, userspace WireGuard, node enrollment, real deployments,
distributed leases, or a claim that `flock` coordinates multiple hosts.

## 1. Execution identity

Three identifiers with distinct jobs:

| Name | Form | Purpose |
| --- | --- | --- |
| Execution identity | `op_<32hex>:<attempt>:<step>` | Who owned one node task invocation. Persisted in the node journal and, while running, in PostgreSQL. |
| Effect key | `op_<32hex>:<step>` | Stable identity of the side effect. Stable across attempts so a retry can find work a prior attempt completed. |
| Request ID | random 128-bit hex | Correlates one transport call with node-side diagnostics and a lost response. Never used to deduplicate effects. |

Step IDs are versioned and deterministic, for example `diagnostic-step-01-v1`, so the
same operation input always names the same effects. `attempt` is River's attempt number
and is used for ownership/progress fencing, never to create a second effect key.

The worker has two questions before touching the node:

1. **Did the database already acknowledge this step?** Read
   `eregion_operation_steps` by `(operation_id, step)`.
2. **Did the node already complete or start this effect?** Call the transport
   `status` method by effect key.

Only when the database has no completed row and the node is not live-running does it
dispatch `run`. This is the "never blindly start a second execution" rule.

## 2. Journal location and schema

Node-local state directory, resolved from `EREGION_NODE_STATE_DIR`:

- default for a non-root CLI process: `$XDG_STATE_HOME/eregion/node`, falling back to
  `$HOME/.local/state/eregion/node`;
- every worker process on one host must share one state directory; the documented
  service configuration sets an explicit root-owned path such as
  `/var/lib/eregion/node`;
- tests always inject a temporary directory.

Layout, all node-local and mode 0600 where writable:

```text
<state>/journal.json
<state>/journal.json.lock
<state>/host.lock
<state>/locks/<sha256(effect_key)>.lock
<state>/effects/<operation_id>/<step>.json
```

`journal.json`, schema 1:

```json
{
  "schema": 1,
  "node": "local",
  "updated_at": "2026-10-20T12:00:00Z",
  "tasks": {
    "op_aaaa...:diagnostic-step-01-v1": {
      "operation_id": "op_aaaa...",
      "step": "diagnostic-step-01-v1",
      "attempt": 2,
      "execution_id": "op_aaaa...:2:diagnostic-step-01-v1",
      "request_id": "...",
      "inputs_hash": "<sha256>",
      "status": "running|completed|failed",
      "owner": {"pid": 123, "boot_id": "...", "token": "..."},
      "started_at": "...",
      "completed_at": "...",
      "applied_attempt": 1,
      "error": "",
      "result": {}
    }
  }
}
```

The effect record written by a step contains at least `operation_id`, `step`,
`inputs_hash`, `applied_attempt`, `execution_id`, and a result. It is the durable record
of the side effect; the journal records the engine's view of it. A crash between the
effect record and the journal update is recovered by `status` reading the effect record,
or by Check finding the effect present.

- Writes are atomic: temp file, write, chmod, fsync, rename, directory fsync. The mode
  is set before fsync so it is durable.
- The journal is keyed by effect key. It records the latest owner attempt and, when
  completed, the attempt that actually applied the effect (`applied_attempt`).
- A corrupt/unreadable journal is an explicit `precondition_failed`; it is never
  silently reset. Recovering means inspecting and moving it aside deliberately.
- `Inputs()` returns canonical bytes of every input that affects Apply. Secret input
  fields are represented by a domain-separated SHA-256 digest (`sha256("eregion/inputs/v1\x00" + value)`),
  never plaintext. This is a change detector, not a secret store: low-entropy secrets
  must be referenced by revision rather than embedded, and M0.3 diagnostics accept no
  secret input. The journal and step rows keep only the final `inputs_hash`; they never
  store the canonical input bytes.
- `inputs_hash` here means the step's canonical `Inputs()` hash. It is deliberately
  distinct from `eregion_operations.input_hash`, which binds normalized operation input
  for submission idempotency.
- Shell output is line-streamed and redacted through the request-scoped secrets
  registry before it becomes an event, a log line, or a journal error. Script inputs
  travel only through the environment.
- Atomic managed-file writes use temp+chmod+fsync+rename+dirsync. The test effect uses
  create-once semantics (temp + hard link, no replace) so a duplicate application
  cannot overwrite the record of the original effect.

## 3. Mutations, locks, and ownership fencing

Lock ordering is fixed to avoid cycles:

- Node: effect lock → global host lock → journal lock.
- Database: operation row lock → step-row write → event append, all in one short
  transaction.

Node-side:

- Each effect has an exclusive `flock`. Acquiring it is the liveness test: the kernel
  releases a dead process's lock, while a live owner makes a competing run block.
  PID/boot ID/token are kept for diagnostics. `status` tries the effect lock without
  waiting; success means the journal's `running` entry is stale. It releases the lock
  immediately and reports `stale`, never `running`.
- `run` acquires the effect lock (bounded by the caller's deadline), re-reads the
  journal under it, and re-checks the effect record. It runs Check, then Apply once,
  writes the effect record, and finally writes `completed`. Before every terminal
  journal write it compares the stored claim token with its own; a mismatch aborts
  rather than overwriting another claim.
- A global host lock serializes actual Apply mutations. Status and Check do not take it.
- The node-side lock/fencing is a local-host guarantee. PostgreSQL row locks and the
  unique `(operation_id, step)` acknowledgement fence control-plane state. Neither is a
  distributed lock. Multiple control-plane instances can race, but the node serializes
  local effects and the database deduplicates acknowledgements.

Control-plane-side attempt fencing:

- Every domain write done by a worker uses `SELECT ... FOR UPDATE` and then checks
  `op.attempt == job.Attempt` before changing state, events, or steps. A stale attempt
  cannot append events or terminalise the operation.
- A stale attempt (database attempt greater than its River attempt) does not write and
  does not return immediately while the newer attempt is live. It waits, without
  domain writes, until the operation is terminal or its context ends, so it cannot
  complete the shared River row while newer work is still in flight. River's completion
  query is not attempt-fenced; this wait is the mitigation, and it is documented as a
  local-worker limitation rather than a distributed lease.

Conflict scopes in this increment:

| Scope | Mechanism | Protects |
| --- | --- | --- |
| Operation | `SELECT ... FOR UPDATE` + attempt equality | state/event ordering and attempt fencing |
| Step acknowledgement | PK `(operation_id, step)` + conditional update | duplicate DB acknowledgements/events |
| Node effect | effect `flock` + journal/effect record | duplicate local side effects |
| Host mutation | global node `flock` | local concurrent host writes |

Broader resource/node conflict scopes are deferred with remote transports.

## 4. Reconciliation algorithm

Total decision table per step, evaluated in this order:

| DB step | Node status | Hash | Action |
| --- | --- | --- | --- |
| completed | any | matches | Skip. Already acknowledged. |
| completed | any | differs | `precondition_failed`; never re-apply or silently succeed. |
| absent/running/failed | completed | matches | Acknowledge in PostgreSQL; emit one recovery event; do not run. |
| absent/running/failed | completed | differs | `precondition_failed`; do not run. |
| absent/running/failed | absent | — | Run (Check then Apply once). |
| absent/running/failed | stale | — | Run under the effect lock; Check decides whether the interrupted Apply completed. |
| absent/running/failed | running (live) | — | Attach: call `run`, which blocks on the effect lock and then returns the completed result. Never start a parallel Apply. |
| absent/running/failed | failed | matching | Run again; Check decides whether the effect is complete. |

Worker sequence per operation attempt:

1. Load the operation under its row lock. If terminal, stop. If a newer attempt owns it,
   wait without writing until terminal or context end.
2. Reconcile any completed-but-unacknowledged effects before deciding cancellation.
3. If step rows show every step complete, transition to `succeeded` (even when a
   cancellation request is present: the work finished before the last boundary).
4. If `cancelling`, transition to `cancelled`; start no new step.
5. Mark the attempt running and stream a step-start event containing the execution
   identity.
6. For each deterministic step in order:
   1. Check the cancellation boundary (below).
   2. Apply the decision table.
   3. `run` returns `completed` (possibly with `executed=false` when it recovered an
      effect) or an error. A failed step is recorded as `failed` in the journal.
      Retryable failures are returned until the attempt bound is reached; permanent
      failures (an effect recorded under other inputs, or a corrupt/incompatible
      marker) fail the operation immediately without another Apply.
   4. Begin/acknowledge the step in one short PostgreSQL transaction: upsert the
      `running` row before dispatch; on completion, conditionally update it to
      `completed` and only when `RowsAffected()==1` set `completed_steps` from the
      completed-row count and append exactly one progress event.
7. After the last acknowledgement, transition to `succeeded`.

Failure between effect and acknowledgement is tested by injecting an error immediately
after the node returns and before the acknowledgement transaction. The next attempt
must recover from node `status` and produce one effect, one step row, one progress
event, and a terminal `succeeded`.

`Reconcile` consults node status before declaring failure. A discarded job whose node
effect is still live-running is left `running` with a warning; a completed effect is
acknowledged and may finalize success; an absent/stale effect with no job becomes
`failed` (or `cancelled` when a cancellation was requested).

## 5. Cancellation model

Detaching a viewer or client is never cancellation:
- the API client closing a connection only ends that request;
- `operations get/events` have no side effect;
- `RequestCancel` is the only cancellation path.

Explicit cancellation semantics:
- Cancellation is requested by setting `cancelling`; it is an observation/request, not an
  acknowledgement.
- Boundaries are per step and declared by the step: `before_apply` (may skip without a
  side effect), `after_apply` (the in-flight step finishes and is acknowledged, then
  cancellation is honoured), or `never` (must finish; only for short, atomic effects).
- Every diagnostic step declares `after_apply`.
- The worker checks the boundary before starting each step and after acknowledging one.
  It never sends a mid-step kill for a cancellation request. If it observes
  `cancelling` before a step, it transitions to `cancelled` without starting that step.
  If the final step had already completed, it transitions to `succeeded` and records
  that cancellation arrived after the last boundary.
- Process shutdown or River's job deadline is not a cancellation request. If it
  interrupts a step, the journal remains `running` and the next attempt reconciles it;
  the step must be idempotent/Checkable. The test suite includes this path.
- Cancellation does not roll back completed effects. Events record completed steps.
- No node-level cancel RPC or mid-step kill is implemented; future interruptible steps
  must declare a cooperative boundary before using one.

## 6. Transport boundary

One interface, two adapters eventually:

```go
type Transport interface {
    Name() string
    Call(ctx context.Context, request Request, onEvent func(Event)) (Response, error)
}
```

`Request` carries method (`run`, `status`), request ID, execution identity, effect key,
canonical inputs, and optional transient secrets. `Response` carries state (`absent`,
`running`, `stale`, `completed`, `failed`), `executed`, ownership detail, and result. The
local adapter calls the in-process dispatcher directly. A future SSH adapter sends the
same request over pinned SSH; a WireGuard adapter changes only how the SSH connection is
dialled. Workers depend solely on `Transport`.

`run` never returns a cancelled state: the node has no database access and cancellation
is decided by the worker at step boundaries. A transport test double can dispatch
successfully and then return a stream-lost error; the retry must recover through
`status`.

## 7. Database change (migration 002)

The current migrator embeds one blob and compares one checksum, so this increment must
first make migrations versioned: an ordered embedded list, per-version checksums, an
ordered apply loop, and `schemaVersion=2`. Existing v1 rows and their 001 checksum stay
unchanged; editing applied migration text still fails closed.

```sql
CREATE TABLE eregion_operation_steps (
    operation_id text NOT NULL REFERENCES eregion_operations(id),
    step         text NOT NULL,
    inputs_hash  text NOT NULL,
    state        text NOT NULL CHECK (state IN ('running','completed','failed')),
    attempt      integer NOT NULL CHECK (attempt >= 0),
    execution_id text NOT NULL,
    started_at   timestamptz NOT NULL DEFAULT clock_timestamp(),
    completed_at timestamptz,
    error        text NOT NULL DEFAULT '',
    result       jsonb,
    PRIMARY KEY (operation_id, step)
);

CREATE INDEX eregion_operation_steps_incomplete
    ON eregion_operation_steps (operation_id) WHERE state <> 'completed';
```

River arguments remain `{operation_id}` only. No secret material enters River rows,
events, or step rows.

## 8. Test plan

Unit (`internal/engine`, `internal/node`):
- Check/Apply skip with matching inputs hash; re-apply on changed inputs, previous
  failure, or interrupted `running` journal entry.
- Secret inputs are hashed; journal/logs/events never contain plaintext.
- Atomic write ordering and create-once semantics; corrupt journal fails closed;
  leftover temp files are ignored.
- Shell redaction, non-zero exit, baseline output tail, cancellation grace.
- `flock` contention and release; status uses lock acquisition, not PID reuse.
- Duplicate/concurrent `run` of one effect executes once; the second returns
  `completed, executed=false` and the applied attempt is unchanged.
- Status reports absent/running/stale/completed/failed honestly; a live owner is not
  preempted.

PostgreSQL integration:
- Existing submission, retry, crash-rescue, and API/worker tests adapted to the node
  state directory.
- Fail between node effect and DB acknowledgement: retry recovers; one effect file,
  one step row, one progress event, terminal `succeeded`.
- Transport loses the response after a successful dispatch: retry recovers through
  `status` without re-running.
- Concurrent duplicate submissions with one idempotency key: one operation, one job,
  one effect per step. A different key is a distinct operation and is documented.
- Lost final acknowledgement: retry finalizes without re-running effects.
- Cancellation before start: no effects; cancellation during a step: completed step is
  acknowledged, no later effects, honest terminal state. A test hook blocks before
  Apply so the cancel window is deterministic.
- Client detach/reconnect does not cancel and does not duplicate effects.
- Worker process crash (SIGKILL) and graceful SIGTERM mid-step: the rescued attempt
  reconciles a stale journal entry and completes exactly once.
- `Reconcile` does not mark an operation failed while its node effect is live-running.
