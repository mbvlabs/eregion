# M0.3 remote half plan: userspace WireGuard (Increment B)

**Status:** Planned · 2026-10-20
**Scope:** Increment B of [the SSH/WireGuard increments](ssh-wireguard-next.md) only.
It builds on [the M0.3 SSH plan](m0.3-ssh-plan.md) and changes none of its
decisions.

Increment B adds one thing: a `Dialer` that gives the pinned SSH transport its
`net.Conn` through a userspace WireGuard tunnel. The SSH transport, host-key
pinning, the node protocol, the node binary, the worker, the operation contract,
the River arguments, and the PostgreSQL step model do not change.

## Decision summary

| # | Question | Decision |
| --- | --- | --- |
| 1 | Library | `golang.zx2c4.com/wireguard` (`device`, `conn`, `tun/netstack`) on gVisor netstack, pinned to `v0.0.0-20261006164505-2631ce99a06f`. No TUN device, no root, no kernel interface on the control plane. |
| 2 | Layering | SSH runs *inside* the tunnel. The SSH address is the node's tunnel address. The host key is still pinned; WireGuard adds a network fence, it does not replace SSH authentication. |
| 3 | Private key | Read from a file that must be a regular file with no group or other permission bits. Never taken from an environment variable value, an argument, a log, River, or the database. Registered for redaction in base64 and hex form. |
| 4 | Selection | `EREGION_NODE_TRANSPORT=ssh` as today, plus `EREGION_NODE_WG_PRIVATE_KEY_FILE`. The WireGuard dialer is used exactly when that variable is set. The transport name stays `ssh`; command metadata lists the `EREGION_NODE_WG_*` variables. |
| 5 | Lifecycle | One tunnel per process, shared by every call. Handshake on the first dial, bounded by a handshake timeout. Persistent keepalive. A liveness probe declares the tunnel lost. The next dial rebuilds it. The worker shutdown closes it. |
| 6 | Failure meaning | A tunnel that cannot come up is a `TunnelDownError` *before* any SSH byte, so no request is dispatched. A tunnel lost after dispatch surfaces through the SSH transport as `node.ErrStreamLost`, never as proof the node task stopped. |
| 7 | Test node | Kernel WireGuard (`ip link add type wireguard`) inside the SSH fixture container with `NET_ADMIN`. Only the UDP port is published; SSH is reachable only through the tunnel. Tests skip cleanly without Docker, without `NET_ADMIN`, or without the kernel module. |
| 8 | Supervision | Unchanged from SSH: a detached node task plus a durable journal queried by `status`. The tunnel owns no execution lifetime. |

## 1. Library and dependency cost

- `golang.zx2c4.com/wireguard` is the reference userspace implementation, the
  same code as `wireguard-go`. It has no tagged releases, so the module is pinned
  to a pseudo-version: `v0.0.0-20261006164505-2631ce99a06f` (2026-10-06). The
  sibling project `vaire` already runs this version against kernel WireGuard nodes.
- `tun/netstack` gives a TCP/IP stack in the process (gVisor
  `v0.0.0-20250503011706-39ed1f5ac29c`), so the control plane needs no TUN
  device, no `CAP_NET_ADMIN`, and no routing changes.
- Measured cost: six new modules in `go.mod` (`wireguard`, `wintun`, `gvisor`,
  `golang.org/x/net`, `golang.org/x/time`, `github.com/google/btree`; all but the first
  are indirect). The `eregion` binary grows from 20.5 MB to 23.2 MB (+2.7 MB,
  +13 %). The node binary does not import it.
- Rejected: kernel WireGuard on the control plane (needs root and system
  configuration, which the increment forbids). Also rejected: a WireGuard
  implementation written by hand (a crypto protocol is not a place to save a
  dependency).

## 2. Layering and identity

```text
worker -> SSHTransport -> WireGuardDialer.DialContext("tcp", "10.77.0.2:22")
                                  |
                       netstack TCP inside the tunnel
                                  |
              wireguard-go device  --UDP-->  node wg0 (kernel)  -> sshd
```

- The SSH address (`EREGION_NODE_SSH_ADDRESS`) is the node's **tunnel**
  address. The `known_hosts` pin is written for that address.
- The node's WireGuard public key pins the tunnel peer, and the SSH host key
  pins the SSH server. Both must match. A node with the right WireGuard key and
  the wrong host key is still refused with `HostKeyMismatchError`.
- The dialer refuses an address outside the allowed IPs at once, without
  sending anything. It reports a configuration error, not a timeout.

## 3. Control-plane configuration

| Variable | Meaning | Validation |
| --- | --- | --- |
| `EREGION_NODE_WG_PRIVATE_KEY_FILE` | Path to the control plane's WireGuard private key (`wg genkey` output). | Regular file, no group/other bits, one base64 32-byte key. The path is not a secret; the content is. |
| `EREGION_NODE_WG_ADDRESS` | The control plane's own tunnel address, for example `10.77.0.1`. | A single IP address. |
| `EREGION_NODE_WG_PEER_PUBLIC_KEY` | The node's WireGuard public key. | Base64 32 bytes; must not equal our own public key. |
| `EREGION_NODE_WG_ENDPOINT` | The node's UDP endpoint, `host:port`. | The host may be a name; it is resolved each time the tunnel comes up, so a reconnect follows a changed address. |
| `EREGION_NODE_WG_ALLOWED_IPS` | Comma-separated prefixes routed to the node. Defaults to the node's tunnel address as a `/32` or `/128`. | No default route; no IPv4 prefix shorter than `/16`, no IPv6 prefix shorter than `/48`. Must contain the SSH address. |
| `EREGION_NODE_WG_KEEPALIVE` | Persistent keepalive in seconds. Default `25`. | 1 to 3600 seconds. |

- **Why a file and not a value.** An environment variable value appears in
  `/proc/<pid>/environ`, in crash dumps, and in process supervisors' logs. A
  file with a strict mode is the same rule the SSH identity already follows.
  There is deliberately no `EREGION_NODE_WG_PRIVATE_KEY` variable.
- **Where the key lives in memory.** The key is parsed into a `WireGuardKey`
  value whose `String`, `GoString`, `MarshalJSON`, and `LogValue` all print
  `[REDACTED]`. A `%+v` of the configuration therefore never prints it. The
  dialer hands it to `wireguard-go` through the in-process UAPI only. The
  wireguard-go logger is wired to discard verbose output and to pass errors
  through the redacting log writer.
- **Redaction.** The CLI registers the base64 and hex forms of the private key
  in the invocation's secret registry before it builds anything, so any log line,
  error, or output that contains them is redacted.
- **Never persisted.** The worker only sees `node.Transport`. No WireGuard value
  is in a `node.Request`, a River argument, an event, or a row. The integration
  suite scans every `eregion_*` table and `river_job` for the key.
- **Metadata.** `serve` and `worker` list the six `EREGION_NODE_WG_*` variables
  next to the SSH ones in `nodeTransportEnvironment`. No flag is added: every
  transport value comes from the environment, as for SSH.

## 4. Lifecycle

The dialer has four states: `down`, `handshaking`, `up`, `closed`.

1. **First dial.** The dialer is `down`. `DialContext` creates the netstack
   interface and the `wireguard-go` device, configures the peer through UAPI,
   and brings the device up. It then sends one ICMP echo to the node's tunnel
   address to start a handshake, and waits until UAPI reports a non-zero
   `last_handshake_time`. Concurrent dials share one bring-up.
2. **Bounded failure.** If the handshake does not complete within the
   handshake timeout (default 10 s, which is two WireGuard handshake attempts)
   or the caller's deadline, the device is torn down and the dial returns
   `*TunnelDownError`. No TCP connection was opened and no SSH byte was sent,
   so no request can have been dispatched.
3. **Reuse.** While `up`, every dial opens a netstack TCP connection inside the
   same tunnel. The SSH transport still opens one SSH connection per `Call`, as
   it does today; only the tunnel is shared.
4. **Keepalive.** Persistent keepalive (default 25 s) keeps NAT mappings open.
5. **Liveness.** While `up`, a probe runs every probe interval (default 2 s).
   When the tunnel received nothing since the last tick (UAPI `rx_bytes` did
   not move), it sends one ICMP echo to the node's tunnel address. A healthy
   node answers it, so `rx_bytes` moves. When nothing was received for the loss
   threshold (default 15 s, the same as WireGuard's own
   keepalive-plus-rekey timeout), the tunnel is **lost**: every open connection
   is closed with `ErrTunnelLost`, the device is torn down, and the state returns
   to `down`.
6. **Reconnect.** The next dial after a loss performs a fresh bring-up and
   handshake (step 1). An established SSH connection is never moved to a new
   tunnel. It fails, and the caller's retry path asks for `status` first.
7. **Shutdown.** `Close` closes every connection and the device, and makes later
   dials fail. The CLI calls it after `stopWorkers`, so a worker that stops
   cleanly leaves no UDP socket or goroutine behind.

The probe, interval, and thresholds are fields on `WireGuardConfig` with the
defaults above. Tests shorten them. The environment exposes only the keepalive.
The other values are protocol tuning, not deployment configuration.

## 5. Failure meaning

| Situation | What the caller sees | Dispatched? |
| --- | --- | --- |
| Handshake never completes (node down, wrong keys, blocked UDP) | `*TunnelDownError` wrapped by the SSH dial error. Retryable, not permanent. | No. Nothing passed the tunnel. |
| Address outside the allowed IPs | A configuration error from the dial. Not permanent, but it cannot pass a retry; `NewWireGuardDialer` checks it up front, so it shows at startup. | No |
| Tunnel lost while a request or status poll is in flight | `node.ErrStreamLost` from the SSH transport, with `the WireGuard tunnel to … was lost` in the detail. | Maybe. The outcome is unknown. |
| Tunnel lost while idle | Nothing until the next dial, which rebuilds the tunnel. | n/a |

- Wrong keys look the same as a node that is down: WireGuard is silent to
  unauthenticated peers on purpose. A handshake failure is therefore
  **retryable**, not permanent, and its message names the endpoint, the peer
  public key, and the timeout, so the operator can check the keys.
- A lost tunnel is never a statement about the node task. The task is detached,
  as for SSH. The worker's retry calls `status` before `run`. The node's effect
  lock and effect record keep a second run from applying the effect twice.
- `TunnelDownError` is not `ErrStreamLost`. Tests check both directions: a
  handshake failure is not a lost stream, and a loss after dispatch is not a
  handshake failure.

## 6. Test node

`sshfixture.Options{WireGuard: true}` starts the same SSH fixture container with:

- `--cap-add NET_ADMIN`, and the image gains `wireguard-tools` and `iproute2`;
- a kernel `wg0` interface with a generated node key, listen port 51820, the
  node address `10.77.0.2/24`, and the control plane's public key as its only
  peer (`allowed-ips 10.77.0.1/32`);
- only `51820/udp` published on loopback. The SSH port is **not** published, so
  every SSH byte provably crosses the tunnel;
- a generated control-plane private key file (mode 0600) and a `known_hosts`
  pin for `[10.77.0.2]:2222`.

Kernel WireGuard on the node is the deployment shape, and it tests real
interoperability between `wireguard-go` and the kernel implementation. If
`ip link add wg0 type wireguard` fails (no `NET_ADMIN`, no module, rootless
Docker without the capability), `Start` returns `ErrUnavailable` and the test
skips with that reason. Rejected: `wireguard-go` with a TUN device in the
container (it needs `/dev/net/tun` and `NET_ADMIN` too, and tests a less
realistic node). Also rejected: a userspace relay that terminates the tunnel in
the test process (it would not test a real node).

Fault injection uses a UDP relay (`sshfixture.UDPRelay`) in front of the
published WireGuard port. A test can black-hole it in both directions. That is
a real tunnel loss: the WireGuard session stops and nothing in TCP or SSH sees a
reset. The relay counts the packets it dropped, so a test can prove that the
loss happened.

`just wireguard` runs the WireGuard transport tests. `just ssh-fixture` builds
the extended image.

## 7. Tests

Transport package, against the WireGuard fixture:

- tunnel up, status, and reuse (two calls, one handshake);
- tunnel down: a black-holed relay gives `TunnelDownError` within the
  handshake timeout, with zero effects on the node and no node journal entry;
- handshake failure with a wrong peer key dispatches no work;
- reconnect: after the black hole lifts, the next call brings the tunnel back
  and succeeds;
- lost tunnel after dispatch: black-hole the relay while the node task runs. The
  call returns `ErrStreamLost`, not `TunnelDownError`. After the black hole
  lifts, `status` reports the completed effect, and a retried `run` produces no
  second effect;
- the right WireGuard peer with the wrong pinned host key is still refused;
- `Close` makes later dials fail and closes open connections.

Unit tests without Docker: key parsing and file-mode checks, allowed-IP
validation, the redacted `String`/`MarshalJSON`/`LogValue`, and a `%+v` of the
configuration.

CLI: the environment wiring builds the dialer, the key is registered in the
secret registry, a missing or world-readable key file is refused, and the
metadata lists the variables.

Control-plane integration over SSH-over-WireGuard, with the same scenarios as
the SSH suite: the diagnostic run, a lost response (a black hole after dispatch),
a killed worker (helper process with the WireGuard environment), duplicate
submissions, cancellation at a step boundary, and a node task that outlives its
caller. Each test also scans the persisted rows and the captured worker log for
the key.

## 8. Supervision

Unchanged from [the SSH plan](m0.3-ssh-plan.md) section 1: a detached node task
plus a durable journal, queried by `status`. The tunnel is a transport like the
SSH channel. Losing it never kills the node task and never implies that the task
stopped. The cancellation and fencing decisions (no remote kill, the effect lock
and effect record as the fence) carry over as they are.

## 9. Non-goals

Node enrollment and key distribution, key rotation, more than one peer per
process, roaming of the control plane, a WireGuard mesh, DNS inside the tunnel,
and kernel WireGuard on the control plane. The roadmap item is ticked only when
the WireGuard endpoint passes the exactly-once scenarios above.
